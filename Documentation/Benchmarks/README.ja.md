# EditorでのCPU処理時間の比較

2026-10-28にUnity Editorで2つの物理エンジンの処理時間を比較しました。この文書では、[プロジェクトのREADME](../../README.ja.md)に掲載した表とグラフの測定条件と集計方法を説明します。

## 比較したもの

戦闘が進むとユニットが死亡し、処理量も減っていきます。死亡するタイミングはエンジンによって異なるため、速度の比較には死亡を無効にして人数を保つ固定負荷を使いました。実際の戦闘での動作も分かるように、死亡と勝敗のある通常戦闘も別に測定しています。

| 実験 | 各陣営の人数 | 表示条件 | 繰り返し | 実行数 |
|---|---|---|---|---:|
| 通常戦闘（`Battle`） | 25 / 100 / 250 | 表示更新なし / mesh更新あり | 各条件5回 × 両エンジン | 60 |
| 固定負荷（`FixedLoad`） | 25 / 100 / 250 / 1,500 / 2,500 | 表示更新なし / mesh更新あり | 各条件5回 × 両エンジン | 100 |
| 合計 | | | | **160** |

通常戦闘は、最初のステップから決着がつくか1,800ステップに達するまで記録しました。固定負荷では死亡と勝敗の反映だけを無効にし、移動、敵探索、接触、攻撃範囲の照会は続けています。120ステップの準備後、121〜720ステップの600標本を収集しました。

表示更新を行わない`NoView`でも戦闘ロジックは動きます。物理計算だけを取り出した実験ではありません。`Mesh`では、これに加えて共通の表示コード`BattleWorldView.Refresh`を毎ステップ呼び、位置とアニメーションを更新します。ここで測るのはmeshデータの更新時間であり、GPUの描画時間は含みません。

## 条件の揃え方

各組み合わせで、同じ`BattleInput`を両エンジンに渡しました。seedは12345、1ステップのシミュレーション時間は1/60秒です。実行順はLegacy→CoreとCore→Legacyを交互にしましたが、繰り返しが5回なので、各順序の回数は同じではありません。人数も少ない順に増やしており、順序をランダムにはしていません。

本測定の前に、各エンジンで25対25の戦闘を120ステップずつ実行し、JITコンパイルとmesh更新を一度済ませました。この準備戦闘と予備実行8回の標本は結果から除外しています。測定中は実時間の経過を待たず、描画1フレームにつき最大8ステップを処理しました。ゲーム内の1倍速・2倍速や、実時間でのフレーム性能とは区別する必要があります。

通常の戦闘が並行して動かないように、通常の開始用コンポーネントを無効にし、UIとカメラの自動追従も停止しました。背景は残していますが、画面内に入る兵力の数は比較条件にしていません。標本配列は事前に確保し、文字列処理とファイル保存は測定区間の外で行いました。ただし、戦闘コードやエンジン内部のメモリ確保までなくしたわけではありません。

各実行後に表示オブジェクトと物理オブジェクトを解放し、2フレーム待ちました。その後、Rigidbody2Dが0個、Coreはデフォルトworldの1個だけであることと、従来の物理実行モードが復元されたことを確認しました。開始時と終了時のbody・shape数も、生存数に境界4個を加えた値と照合しています。

同じPCでの分析、テスト、グラフ作成は測定終了後に行いました。ただし進捗ファイルは時々読み込んでおり、OS上のほかの処理まで統制した専用の測定環境ではありません。

## 環境と物理設定

実際の環境は[environment.txt](2026-10-28/environment.txt)に記録しています。

| 項目 | 設定 |
|---|---|
| Unity | 6000.5.8f1、Built-in、Mono Editor |
| OS・CPU | Windows 11、Ryzen 7 7800X3D、論理プロセッサ16基 |
| メモリ・GPU | RAM 64,681 MB、RTX 5070 Ti |
| 画面 | Direct3D12、1920×1080 |
| 実行オプション | VSync 0、フレーム制限 -1、Profiler記録オフ |

各実行の`*.config.txt`には物理設定があります。CoreはScriptモードでsubsteps 4、workers 16を使い、スリープを許可しました。接触設定は`contactFrequency=30`、`contactDamping=10`、`contactSpeed=3`、円形shapeの密度は`1/(πr²)`です。自動CCDのしきい値0.5は、実装コードの設定説明として記録したものです。

従来方式もScriptモードで動かし、velocity iterations 8、position iterations 3、Discrete、StartAwake、質量1を使いました。両エンジンの計算精度を同等に揃えた比較ではなく、worker数やsubstepを変えた比較もしていません。そのため、測定した差をマルチスレッドやデータ構造など、個別の要因の効果に分けて説明することはできません。

## 測定値の読み方

`Stopwatch`で関数の呼び出しから戻るまでの経過時間を測りました。物理計算、攻撃照会、共通ロジック、位置取得、表示更新を分けて記録しています。各CSV列の範囲は次のとおりです。

| CSV列 | 測定した処理 |
|---|---|
| `native_ms` | 物理エンジンの同期的な`Simulate`呼び出し |
| `query_ms` | 攻撃範囲の照会と候補の検証。Coreの結果配列の生成・解放を含む |
| `logic_ms` | AI、標的選択、速度設定、死亡処理などの共通ロジック |
| `extract_ms` | 物理オブジェクトの位置を共通ユニット配列に読み込む処理 |
| `view_ms` | 共通meshの位置・アニメーションデータの更新。`NoView`では0 |
| `total_ms` | `Battle.Step`と任意のmesh更新を合わせた全体時間。計測呼び出しのコストも一部含む |
| `creation_ms` | 物理実装と`BattleSimulation`の生成。mesh生成と地面更新は除く |

これらは複数のCPU workerスレッドの使用時間を合計した値ではありません。フレーム全体の時間、GC割り当て量、GPU、メモリも収集していません。`NoView`で`view_ms`が0なのは表示更新を呼んでいないという意味で、メモリ確保がないという意味ではありません。CSVにはミリ秒を小数点以下6桁まで保存していますが、その桁数の測定精度を保証するものではありません。

## 表とグラフの集計方法

各実行のp50とp95は、標本を並べて`ceil(n×p)-1`の位置を選ぶnearest-rank法で求めました。[集計CSV](2026-10-28/aggregate.csv)と[統計表](2026-10-28/tables.ja.md)では、こうして得た実行ごとの統計値5個の中央値を示しています。「平均」の列も、各実行の平均を求めてから、その5個の中央値を取ったものです。

最初のグラフは、5回の実行の中央値から、さらに中央値を取っています。縦軸は対数目盛で、エラーバーはその5個の最小値と最大値です。信頼区間や全標本の範囲を示すものではありません。

処理区間別の積み上げ棒グラフは集計方法が異なります。各実行の区間別平均を5回分で算術平均し、それを積み上げています。中央値を足したグラフではないため、統計表とは数値が異なる場合があります。敵探索などが特定のステップに集中すると平均やp95が中央値より大きくなることもありますが、遅いステップの原因を関数ごとに追う分析は行っていません。

## コードと結果ファイル

[EditorComparison.cs](EditorComparison.cs)が測定に使ったコードです。`Assets`の外に置き、Unity CLIからメモリ上でコンパイル・実行したため、保存済みのシーンやゲームコードに一時的な測定機能は追加していません。[analyze.py](analyze.py)はCSVを読み、統計を確認して表とグラフを作ります。2つのグラフには作者名**hakrimryu**を入れています。

分析では32通りの組み合わせを各5回、合計160回・90,579標本を確認しました。標本のステップが連続していること、固定負荷で生存数が維持されていることを検査し、物理と全体処理のp50・p95も再計算しています。[分析の検証記録](2026-10-28/analysis-verification.json)には、この結果と分析ツールのバージョンがあります。

[測定完了記録](2026-10-28/completed.json)には実行ごとの資源解放と設定の復元が、[測定時のファイルハッシュ](2026-10-28/source-sha256.json)にはコード・シーン・パッケージ・設定・測定ツールのSHA256が残っています。

## 結果の解釈

今回の結果は、このEditorシーンで大規模戦闘の物理処理時間が短くなったことを示します。5,000体のCoreでも、mesh更新を含む全体のp95は約21.30 msだったため、ゲーム全体が安定した60 FPSで動くとは判断できません。独立したPlayerの性能や別のCPUでの改善率、メモリ削減も、この測定では確認していません。

戦闘結果の再現性は、速度とは別の話です。今回のセッションではCoreの結果は繰り返しても同じでしたが、プラットフォーム間の決定論を保証するものではありません。従来方式の一部の通常戦闘では、終了ステップや生存数が実行ごとに変わりました。固定負荷でも、両エンジンの接触分布まで一致させてはいません。
