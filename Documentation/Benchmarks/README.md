# Editor CPU 비교 측정

2026-10-28에 Unity Editor에서 두 물리 엔진의 처리 시간을 비교했습니다. 이 문서는 [프로젝트 README](../../README.ko.md)에 실린 표와 그래프를 어떤 조건에서 측정하고 계산했는지 설명합니다.

## 무엇을 비교했는가

전투가 진행되면 유닛이 죽으면서 처리할 일도 줄어듭니다. 엔진마다 사망 시점이 다르기 때문에, 속도를 비교할 때는 사망을 끄고 같은 인원을 유지하는 고정 부하 실험을 사용했습니다. 실제 전투에서의 동작도 볼 수 있도록 사망과 승패를 허용한 일반 전투를 따로 측정했습니다.

| 실험 | 진영별 인원 | 표시 조건 | 반복 | 실행 수 |
|---|---|---|---|---:|
| 일반 전투 (`Battle`) | 25 / 100 / 250 | 표시 제외 / mesh 갱신 포함 | 조건별 5회 × 두 엔진 | 60 |
| 고정 부하 (`FixedLoad`) | 25 / 100 / 250 / 1,500 / 2,500 | 표시 제외 / mesh 갱신 포함 | 조건별 5회 × 두 엔진 | 100 |
| 합계 | | | | **160** |

일반 전투는 첫 스텝부터 승패가 나거나 1,800스텝에 도달할 때까지 기록했습니다. 고정 부하는 사망과 승패 적용만 끈 채 이동, 적 탐색, 접촉, 공격 범위 조회를 계속 실행했고, 120스텝을 준비한 다음 121~720스텝의 600개 표본을 수집했습니다.

표시를 제외한 `NoView`에서도 전투 로직은 그대로 실행됩니다. 물리 계산만 따로 돌린 실험은 아닙니다. `Mesh`에서는 여기에 공통 표시 코드인 `BattleWorldView.Refresh`를 매 스텝 호출해 유닛의 위치와 애니메이션을 갱신했습니다. 이때 측정한 것은 mesh 데이터를 바꾸는 시간이며 GPU가 화면을 그리는 시간은 포함하지 않습니다.

## 같은 조건을 어떻게 맞췄는가

각 조합에서는 같은 `BattleInput`을 두 엔진에 전달했습니다. seed는 12345, 한 스텝의 시뮬레이션 시간은 1/60초로 고정했습니다. 실행 순서는 Legacy→Core와 Core→Legacy를 번갈아 사용했지만 반복이 5회여서 두 순서의 횟수가 같지는 않습니다. 인원도 작은 수부터 늘렸으며 순서를 무작위로 섞지는 않았습니다.

본 측정 전에는 25 대 25 전투를 엔진별로 120스텝씩 실행해 JIT 컴파일과 mesh 갱신을 미리 거쳤습니다. 이 준비 전투와 예비 실행 8회의 표본은 결과에서 제외했습니다. 측정 중에는 실제 시간이 흐르기를 기다리지 않고 프레임당 최대 8스텝을 처리했으므로, 게임의 1×·2× 배속이나 실시간 프레임 성능과는 구분해야 합니다.

기존 전투가 함께 실행되지 않도록 일반 진입 컴포넌트를 해제하고 UI와 자동 카메라 추적도 껐습니다. 씬 배경은 유지했지만 화면에 병력이 얼마나 들어오는지는 비교 조건으로 삼지 않았습니다. 표본 배열은 미리 만들고 문자열 처리와 파일 저장은 측정 구간 밖에서 수행했습니다. 전투 코드나 엔진 내부에서 발생하는 메모리 할당까지 없앤 것은 아닙니다.

한 실행이 끝나면 표시 객체와 물리 객체를 해제하고 두 프레임을 기다렸습니다. 그 뒤 Rigidbody2D가 0개이고 기본 Core world만 1개 남았는지, 기존 물리 실행 모드가 복구됐는지 확인했습니다. 시작과 종료 시점의 body·shape 수도 생존 유닛 수에 경계 4개를 더한 값과 대조했습니다.

같은 PC에서 분석·테스트·그래프 생성은 측정이 끝난 뒤 진행했습니다. 다만 진행 파일을 간헐적으로 읽었고 운영체제의 다른 작업까지 통제한 전용 측정 환경은 아니었습니다.

## 사용 환경과 물리 설정

실제 환경은 [environment.txt](2026-10-28/environment.txt)에 기록했습니다.

| 항목 | 설정 |
|---|---|
| Unity | 6000.5.8f1, Built-in, Mono Editor |
| 운영체제·CPU | Windows 11, Ryzen 7 7800X3D, 논리 프로세서 16개 |
| 메모리·GPU | RAM 64,681 MB, RTX 5070 Ti |
| 화면 | Direct3D12, 1920×1080 |
| 실행 옵션 | VSync 0, 프레임 제한 -1, Profiler 기록 끔 |

실행마다 저장한 `*.config.txt`에는 물리 설정이 있습니다. Core는 Script 모드에서 substeps 4, workers 16을 사용하고 수면을 허용했습니다. 접촉 설정은 `contactFrequency=30`, `contactDamping=10`, `contactSpeed=3`이며 원형 shape의 밀도는 `1/(πr²)`입니다. 자동 CCD 임계값 0.5는 구현 코드의 설정 설명으로 기록한 값입니다.

기존 방식도 Script 모드로 실행했으며 velocity iterations 8, position iterations 3, Discrete, StartAwake, 질량 1을 사용했습니다. 두 엔진의 계산 정확도를 동등하게 맞춘 비교는 아니며, worker 수나 substep을 바꿔 가며 비교하지도 않았습니다. 따라서 측정된 차이를 다중 스레드나 자료 구조 중 한 가지 요인의 효과로 나눠 설명할 수는 없습니다.

## 측정값 읽는 법

시간은 `Stopwatch`로 함수 호출부터 반환까지를 쟀습니다. 물리 계산, 공격 조회, 공통 로직, 위치 읽기, 표시 갱신을 나눠 기록했으며 각 CSV 열의 범위는 다음과 같습니다.

| CSV 열 | 측정한 작업 |
|---|---|
| `native_ms` | 물리 엔진의 동기 `Simulate` 호출 |
| `query_ms` | 공격 범위 조회와 후보 검증. Core 결과 배열의 생성·해제 포함 |
| `logic_ms` | AI, 표적 선택, 속도 적용, 사망 처리 등 공통 로직 |
| `extract_ms` | 물리 객체의 위치를 공통 유닛 배열로 읽기 |
| `view_ms` | 공통 mesh의 위치·애니메이션 데이터 갱신. `NoView`에서는 0 |
| `total_ms` | `Battle.Step`과 선택적인 mesh 갱신을 합친 전체 시간. 계측 호출 비용 일부 포함 |
| `creation_ms` | 물리 구현과 `BattleSimulation` 생성. mesh 생성과 지면 갱신 제외 |

이 값은 여러 CPU 작업 스레드의 사용시간을 합친 값이 아닙니다. 프레임 전체 시간, GC 할당량, GPU, 메모리도 수집하지 않았습니다. `NoView`에서 `view_ms`가 0인 것은 표시 갱신을 호출하지 않았다는 뜻이며, 메모리 할당이 없었다는 뜻은 아닙니다. CSV에는 ms를 소수점 6자리까지 저장했지만 그만큼의 측정 정확도를 보장하지는 않습니다.

## 표와 그래프의 집계 방식

각 실행의 p50과 p95는 표본을 정렬한 뒤 `ceil(n×p)-1` 위치의 값을 선택하는 nearest-rank 방식으로 구했습니다. [집계 CSV](2026-10-28/aggregate.csv)와 [전체 통계표](2026-10-28/tables.md)에서는 이렇게 얻은 실행별 통계 5개를 다시 중앙값으로 묶었습니다. ‘평균’ 열도 각 실행의 평균을 먼저 구한 뒤 그 값 5개의 중앙값을 표시한 것입니다.

첫 번째 그래프는 실행별 중앙값 5개의 중앙값을 보여 줍니다. 세로축은 로그 눈금이고 오차 막대는 그 5개 값의 최솟값과 최댓값입니다. 신뢰구간이나 모든 표본의 범위를 나타내지는 않습니다.

처리 구간별 누적 막대 그래프는 집계 방식이 다릅니다. 각 실행에서 구한 구간별 평균을 5회 산술평균한 뒤 더했습니다. 중앙값을 더한 그래프가 아니므로 통계표와 수치가 다를 수 있습니다. 특정 스텝에 적 탐색 같은 작업이 집중되면 평균과 p95가 중앙값보다 커질 수도 있지만, 느린 스텝의 원인을 함수별로 추적하는 분석은 수행하지 않았습니다.

## 코드와 결과 파일

[EditorComparison.cs](EditorComparison.cs)는 측정에 사용한 코드입니다. `Assets` 밖에 두고 Unity CLI로 메모리에서 컴파일·실행했으며, 저장된 씬이나 게임 코드에 임시 측정 기능을 추가하지 않았습니다. [analyze.py](analyze.py)는 CSV를 읽어 통계를 확인하고 표와 그래프를 만듭니다. 두 그래프에는 작성자 **hakrimryu**를 표시했습니다.

분석 과정에서는 32개 조합을 5회씩 실행한 총 160회, 90,579개 표본을 확인했습니다. 표본의 스텝이 연속되는지, 고정 부하에서 생존 수가 유지되는지 검사하고 물리 계산과 전체 처리의 p50·p95도 다시 계산했습니다. [분석 검증 기록](2026-10-28/analysis-verification.json)에는 이 결과와 분석 도구 버전이 있습니다.

[측정 완료 기록](2026-10-28/completed.json)에는 실행마다 자원을 해제하고 설정을 복구했는지가, [측정 당시 파일 해시](2026-10-28/source-sha256.json)에는 코드·씬·패키지·설정·측정 도구의 SHA256이 남아 있습니다.

## 결과를 해석할 때

이번 결과는 이 Editor 장면에서 대규모 전투의 물리 처리 시간이 줄었다는 근거입니다. mesh 갱신을 포함한 5,000유닛 Core의 전체 처리 p95도 약 21.30 ms였으므로, 게임 전체가 안정적인 60 FPS로 실행된다고 판단할 수는 없습니다. 별도 Player 빌드의 성능이나 다른 CPU에서의 향상률, 메모리 절감 여부도 이 측정으로 확인하지 않았습니다.

전투 결과가 매번 같은지도 성능과 별개입니다. 이번 세션에서는 Core의 결과가 반복해서 같았지만 플랫폼 간 결정론을 보장하지는 않습니다. 기존 방식의 일부 일반 전투는 종료 스텝과 생존 수가 반복마다 달랐고, 고정 부하 역시 두 엔진의 접촉 분포까지 같게 맞춘 실험은 아닙니다.
